## 1. 공공데이터 API 동기화 중 429 에러 및 일일 호출량 초과 문제

- **문제**: 초기 장소 데이터 동기화 중 단시간 호출에 의한 `429 Too Many Requests` 에러가 발생하여 호출 시간을 조정하였지만, <br>API 일일 허용 호출량을 초과하며 동기화가 중단되는 문제가 있었습니다.

<br>

- **해결**: 전체 장소에 대한 상세 정보 호출을 하지 않고, 기본 정보만 우선 저장한 뒤 <br>상세 정보는 사용자가 페이지를 열어볼 때 1건씩 API를 호출하는 마치 지연 로딩과같은 패턴으로 해결하였습니다.

<br>

- **결과**: 불필요한 대량의 API 트래픽을 없애고 429 에러와 일일 호출량 초과 문제를 해결하였습니다.

<details>
<summary><b>상세 보기 (문제 원인 및 해결 과정)</b></summary>
<br>

- **1차 문제 발생**
  - **(429 Too Many Requests)**: 공공데이터 동기화 도중 `429 Too Many Requests` 에러가 반환되며 데이터 수집이 누락되었습니다.
- **원인 분석**
  - 모든 장소의 상세 정보 API(`detailIntro2`)를 반복문으로 대량 연속 호출하면서 공공데이터 포털 서버의 초당 트래픽 한도(TPS)를 순간적으로 초과했습니다.
- **해결 시도**
  - **(딜레이 추가)**: `PoiSyncService` 내 반복문 사이에 200ms 대기 시간을 추가하여 초당 요청 빈도를 조정하려고 하였습니다. (Commit: [699300c](https://github.com/Junho0111/2026-GollaGolla/commit/699300c))

<br>

---

<br>

- **2차 문제 발생**: 
  - **(일일 호출량 초과):** 이번에는 API 일일 허용 호출량을 초과하여 동기화가 완전히 중단되는<br> 문제가 이어서 발생하었으며, 전체 동기화 소요 시간 또한 지나치게 길었습니다.
- **원인 분석**: 
  - 사용자가 당장 조회하지 않을 장소들까지 포함해, 수천 개의 장소에 대한 '상세 정보'를 일괄 조회해 <br>DB에 한 번에 저장하도록 짰기 때문에 불필요한 트래픽 낭비가 심했습니다.
- **해결 과정**: 
  - **(근본적 구조 개편)**: 
    - 200ms 딜레이만으로는 일일 한도 초과와 동기화 지연을 막을 수 없어 JPA의 **지연 로딩 패턴**과 같이<br> 연관 데이터가 호출 되는 시점에 가져오도록 구조를 수정하였습니다.
    - 초기 벌크 동기화 시에는 상세 API 호출을 배제하고, 대신 POI 테이블에 기본 정보와 <br>고유 식별 ID(`source_id`, `content_type_id`)컬럼을 추가하여 저장하도록 구조를 변경했습니다.
    - 장소 상세 조회 시(`PoiQueryService`), DB에 상세 정보가 없을 때만 위에서 추가한 식별 ID를 사용해<br> TourAPI를 단 1건 호출하고 DB를 업데이트하도록 수정했습니다. (Commits: [cdedccc](https://github.com/Junho0111/2026-GollaGolla/commit/cdedccc), [f8a18cb](https://github.com/Junho0111/2026-GollaGolla/commit/f8a18cb))

<br>

- **결과**: 무의미하게 발생하던 대량의 상세 API 호출을 제거하여 429 TPS 초과 에러와 일일 호출량 초과 문제를 해결하였습니다.

## 2. Poi 조회수/찜수 동시성 처리 중 데이터 유실 및 락 충돌 연쇄 발생 해결

- **문제**: 다수의 사용자가 동시에 장소를 조회/찜할 때 카운트가 유실되거나 데드락이 발생하는 문제가 먼저 발생했고, <br>이를 해결하자 단순 조회만으로도 낙관적 락 버전이 상승하여 타 사용자의 리뷰 작성을 방해하는 문제가 발생하였습니다. <br>이후 락을 피하기 위해 트랜잭션을 분리해둔 탓에 일부 로직 실패 시 찜 내역과 찜수 간 정합성이 깨지는 문제가 있었습니다.

<br>

- **해결**: 첫 번째 문제 해결을 위해 독립 트랜잭션(`REQUIRES_NEW`)과 재시도 로직을 도입했고, <br>이어서 두 번째 문제 해결을 위해 카운트 증가 시에는 엔티티 버전을 올리지 않는 부분 업데이트(`@DynamicUpdate`)를 적용했습니다. <br>최종적으로 버전을 안 올리게 되어 락 경합이 사라졌으므로, 찜 저장과 카운트 증가를 다시 단일 트랜잭션(`BEFORE_COMMIT`)으로 묶고 불필요한 데드락 재시도 로직을 제거했습니다.

<br>

- **결과**: 사용자의 단순 조회가 비즈니스 로직을 방해하지 않으면서도, <br>찜 내역 데이터와 카운트 간의 트랜잭션 정합성을 보장하는 구조로 개선하였습니다.

<details>
<summary><b>상세 보기 (문제 원인 및 해결 과정)</b></summary>
<br>

- **1차 문제 발생**
  - **(동시성 데이터 유실 및 데드락)**: 여러 사용자가 동시에 같은 장소(Poi)를 조회하거나 찜을 누를 때, <br>조회수와 찜수가 정상적으로 증가하지 않고 누락(덮어쓰기)되는 동시성 문제가 발생했습니다.
- **원인 분석**
  - JPA 벌크 업데이트 쿼리(`@Modifying`)를 통해 숫자를 올릴 때, JPA의 낙관적 락 기법(`@Version`)이 <br>우회되면서 같은 데이터 행(Row)을 동시에 수정해버리는 문제였습니다. 
- **해결 과정**
  - **(수동 버전 체킹 및 재시도 로직 도입)**:
    - `PoiRepository`의 벌크 업데이트 쿼리에 동시에 쿼리가 들어올때 뭍히는걸 방지하기 위해 <br>수동으로 버전 체킹 로직을 다시 추가하여 안전한 업데이트가 보장되도록 했습니다.
    - `TransactionConfig`에 `REQUIRES_NEW` 전파 속성을 가진 트랜잭션 템플릿을 전역 Bean으로 등록하고 이후 데드락/락 충돌 발생 시 롤백 마킹을 우회하여 <br>최대 3회까지 재시도할 수 있도록 `PoiWishCountEventHandler`에 재시도 로직을 적용했습니다. (Commit: [134c1d0](https://github.com/Junho0111/2026-GollaGolla/commit/134c1d0))

<br>

---

<br>

- **2차 문제 발생**
  - **(락 충돌로 인한 타 비즈니스 방해)**: 위 수정으로 데이터 유실(찜/조회수)은 막았지만, A 사용자가 단순히 장소를 조회해서 조회수가 올라가는 순간, <br>B 사용자가 동시에 해당 장소에 대한 리뷰를 작성하는 등 중요 데이터를 수정하려 할 때 낙관적 락(Lock) 충돌 발생해 B 사용자의 요청이 튕기는 현상이 이어졌습니다.
  >리뷰작성당시 버전이 1이였다면 누군가 조회하는것만으로 버전이 2로 올라가며 이는 리뷰작성자가 완료를 누르는순간 버전이 맞지않아 리뷰가 저장되지않는 문제를 초래함
- **원인 분석**
  - 낙관적 락이 활성화된 상태에서 단순 카운트 증가와 중요 데이터 업데이트가 엔티티의 <br>동일한 버전을 공유(조회수 증가 시 버전 상승)하면서 락 경합이 일어났습니다.
- **해결 시도**
  - **(버전 미증가 처리 및 부분 업데이트)**: 
    - `Poi` 엔티티에 `@DynamicUpdate`를 적용하여 카운트 관련 컬럼만 부분적으로 업데이트하도록 설정했습니다.
    - 단순 조회수 증가나 찜하기 동작 시에는 엔티티의 버전을 올리지 않도록 `PoiRepository` 업데이트 로직을 수정했습니다.
    - 벌크 쿼리의 `clearAutomatically` 설정을 변경하여 의도치 않은 영속성 컨텍스트 초기화로 인한 <br>`LazyInitializationException` 발생 위험도 차단했습니다. (Commit: [445d784](https://github.com/Junho0111/2026-GollaGolla/commit/445d784))
    >벌크 쿼리는 1차 캐시를 무시하고 DB에 바로 쿼리를 날립니다. <br> 즉, DB의 조회수는 2이 되었지만, 1차 캐시(영속성 컨텍스트)에 남아있는 poi 엔티티의 조회수는 여전히 1인 상태(과거 데이터)로 남게 됩니다. <br> 따라서 clearAutomatically=true를 줄시 영속성 컨텍스트가 비워져 이미 조회를 해둔 객체는 준영속 상태가 되며 <br>그 직후 DTO 변환을 위해 poi.getImageUrls() 같은 지연 로딩을 호출하면, 영속성 컨텍스트가 없기 때문에 LazyInitializationException가 터져버립니다.

<br>

<br>

- **3차 문제 발생**
  - **(트랜잭션 분리로 인한 데이터 정합성 불일치)**: 1차 문제 해결을 위해 찜수 증가 로직을 별도의 트랜잭션(`REQUIRES_NEW`, `AFTER_COMMIT`)으로 <br>분리한 상태였습니다. 그러나 이로 인해 '찜 저장'은 성공하여 커밋되었는데, 이후 '찜수 증가' 트랜잭션이 실패할 경우 <br>실제 찜 내역과 Poi의 찜 카운트 숫자가 달라지는 데이터 정합성 불일치 문제가 발생하게 되었습니다.
- **해결 과정**
  - **(단일 트랜잭션 통합 및 불필요한 로직 제거)**: 
    - 2차 해결 과정에서 버전 증가 로직을 제거했으므로 더 이상 찜수 증가 시 다른 로직과 락 경합이나 데드락이 발생하지 않게 되었습니다.
    - 이에 따라 분리했던 트랜잭션을 다시 하나로 합치기 위해 `PoiWishCountEventHandler`의 이벤트를 `AFTER_COMMIT`에서 <br>`BEFORE_COMMIT`으로 변경하여, 찜 저장과 카운트 증가가 **동일한 트랜잭션 내에서 원자적으로** 처리되도록 수정하였습니다.
    - 트랜잭션이 하나로 묶여 충돌 위험이 차단되었으므로, 기존에 데드락을 대비하여 도입했던 3회 재시도 로직과 <br>`TransactionConfig`(REQUIRES_NEW 설정)를 모두 제거하게되었습니다. (Commit: [4972d36](https://github.com/Junho0111/2026-GollaGolla/commit/4972d36))

<br>

- **결과**: 부분 업데이트와 버전 미증가 로직 덕분에 동시성 충돌 문제를 해결하고, 이를 바탕으로 트랜잭션을 다시 하나로 묶어 <br>비즈니스 로직 방해 없이 찜 데이터와 찜 카운트 간의 정합성을 완벽히 보장하는 최종적인 구조로 해결하였습니다.
</details>
